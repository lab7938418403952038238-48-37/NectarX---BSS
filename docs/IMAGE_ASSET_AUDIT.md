# NectarX image asset audit

Generated from the repository tree during the walking/cannon UI update.

## Summary

- **189 image files** are currently committed in the repository.
- The dedicated `NectarX images/` folder contains only its README; the current image library is mostly stored in the repository root.
- NectarX's Screen Reader can now list root-level PNG/BMP files as well as files in `NectarX images/`.
- **Important:** file presence is not proof a template is suitable for screen recognition. Many files appear to be icons, field illustrations, buff/quest artwork, or crops captured for a different scale. Each actual ImageSearch template must be checked in the live Roblox client at the target resolution/UI scale.
- The current image tester is for recognition only. It does not itself enable farming, quest automation, planter automation, or cannon travel.

## Still needed for dependable automation

Do not assume the current asset set covers these reliably until tested or captured from the user's own Roblox setup:

- Backpack-full / pollen meter states and honey conversion confirmation.
- Hive interaction/claim state, cannon prompt and landing/arrival cues.
- Death/respawn and disconnected/loading states.
- Field-specific stable landmark crops for any route that relies on visual navigation.
- Quest progress counters and completion indicators for each supported quest UI.
- Planter ready-to-harvest / planter placed / planter interaction confirmation.
- Any screen state where UI scale, camera angle, lighting, seasonal event, or Roblox update changes the appearance.

## Capture guidance

Capture tight, unscaled crops from the actual Roblox client with the same display scaling and UI scale intended for use. Prefer stable UI text/icons over animated particles or moving world objects. Give each crop a descriptive filename, avoid duplicate crops, and test each template with NectarX's Screen Reader. Keep original source images separately if editing/cropping is needed.

## Walking and cannon support

The UI exposes a saved Walking/Cannon preference. This is a preference only: existing route snippets use legacy helper functions, so the runner must validate route compatibility and implement those helpers before a route is considered executable. A route should only use cannon travel if that route contains compatible cannon steps and the cannon prompt/arrival can be verified.
